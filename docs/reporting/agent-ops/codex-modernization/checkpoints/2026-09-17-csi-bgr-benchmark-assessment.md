## Results

Each pair is NV12 + videoconvert -> direct BGR.

| --- | ---: | ---: | ---: |
| Standalone 640x480/30 | 21.64 -> 4.93 | 29.98 -> 29.98 | 66.91 -> 96.14 |
| Standalone 640x480/60 | 39.14 -> 6.49 | 59.93 -> 59.92 | 70.79 -> 96.24 |
| Standalone 1280x720/30 | 49.77 -> 4.93 | 30.00 -> 30.01 | 87.34 -> 113.62 |
| Standalone 1920x1080/30 | 103.87 -> 5.03 | 24.78 -> 30.01 | 112.21 -> 133.54 |
| PixEagle 640x480/30 | 39.35 -> 21.78 | 29.95 -> 29.66 | 518.57 -> 517.68 |

| PixEagle 1280x720/30 | 79.36 -> 37.64 | 29.99 -> 30.27 | 561.88 -> 560.00 |

720p30 process CPU drops about 90% standalone and 53% in the harness.
System CPU separately falls 12.33% -> 1.31% and 20.28% -> 9.97%, respectively.
Process CPU values appear to use 100% per logical core (standalone exceeds
100%); confirm the collector before quoting these as whole-board percentages.
At 1080p30, mean standalone p95 frame interval improves 55.03 -> 33.41 ms.
These intervals are not camera-to-dashboard latency measurements.

The standalone RSS increase is 21-29 MB; harness RSS decreases 0.9-1.9 MB.
RSS does not measure total system allocation, ISP buffers, or memory bandwidth.
BGR's larger per-pixel payload alone does not establish higher total bus
traffic: removing a CPU conversion also removes reads/writes.

## Limits And Follow-Up

- Both variants fail every standalone 720p60 and 1080p60 run. Both harness
  variants at 720p60 produce zero frames despite an empty error field. Treat
  these as failed acquisitions, never low-CPU successes. Need camera modes and
  GStreamer bus errors to distinguish unsupported timing from pipeline failure.
- Harness 640x480/60 reports 62.63 FPS for NV12 although both variants capture
  about 1206-1207 frames per window. Obtain elapsed-window duration and unique
  frame timestamps before claiming BGR reduces throughput.
- Every successful standalone row records `0x50000`: historical undervoltage
  and throttling bits, with current bits clear. This does not prove throttling
  during these measurements. Record power state before/after subsequent runs.
- No GPU/ISP utilization, sustained load, color correctness, latency, or actual
  detector/follower workload evidence is included. The CSV name `e2e` alone
  does not prove those paths were active.

## Decision

1. Recommend the tested direct-BGR override for CM5/IMX219 now. The benefit is
   substantial; the earlier expectation of a marginal gain was incorrect.
2. Retain the checked-in NV12 template for this assessment. The next runtime
   slice should prefer BGR for the stock Pi path with one NV12 fallback when
   opening/first-frame validation fails. Preserve explicit operator templates,
   use the existing capture lifecycle, release each failed candidate, and
   report the selected path. Avoid sensor-model lists and per-frame probing.
3. Before that slice, obtain the small benchmark harness and exact versions,
   confirm BGR colors/stride and a sustained run with the intended tracker or
   model, and cover failed-BGR/successful-NV12 and both-fail cases in tests.
   Hardware fallback validation needs a stack where BGR is unavailable.
4. Assess Jetson separately. Its existing template already uses hardware
   NV12-to-BGRx conversion; CPU BGRx-to-BGR remains. No comparable Jetson
   improvement is established here. ISP, VIC and CUDA GPU are distinct engines.
